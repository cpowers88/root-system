## The Book's Working Model

A designer has a model of how a system works, but the user never receives that
model directly. The user encounters the **system image**: controls, labels,
documentation, visible state, and feedback. From that evidence, the user builds
a mental model. A design succeeds when the system image lets an ordinary user
build a sufficiently accurate model and recover safely when that model is wrong.

The book's recurring diagnostic is therefore structural:

1. Can the user see what actions are possible?
2. Does the control naturally map to the intended result?
3. Does the system promptly show what happened?
4. Do constraints prevent or narrow invalid actions?
5. Can the user understand the current state and reverse an unwanted result?

## Why It Belongs in SYSTEMS

This is not merely product-design advice. It is a method for investigating
operator error, control-room failure, unsafe automation, confusing workflows,
and interfaces that transfer design complexity onto the user. It strengthens
the same audit principle as [[modeling-process-and-client-ethics]]: robust
systems should allow ordinary people, including tired or stressed people, to
perform safely.

## Limits and Recency

The examples and technology references are historically dated. Use the durable
human-factors principles, not the book as a current interface, accessibility,
or software standard. Modern recommendations still require current domain
standards and observation of actual users.

control panel, or operational process for usability, error, and recovery.

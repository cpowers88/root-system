# Practical SQL: Understanding Data Types

**Summary**: The three core SQL data-type categories — characters, numbers, dates/times — plus auto-incrementing ID columns, JSON/JSONB, and the `CAST()` function for converting between types. Establishes practical defaults (text over varchar, numeric over floating-point for money, bigint over integer when in doubt) backed by concrete demonstrations of where each type's quirks bite.

**Sources**: PracticalSQL.pdf (Anthony DeBarros, 2nd ed., 2022), Chapter 4 ("Understanding Data Types")

**Last updated**: 2026-06-20

---

## Characters

`char(n)` is fixed-length, padding short values with trailing spaces to exactly `n` characters — mostly a legacy pattern now. `varchar(n)` is variable-length up to a max of `n`, storing no padding. `text` is variable-length with no max (up to ~1GB). **There is no real performance difference among the three in PostgreSQL** — the author's stated default is to use `text` everywhere, since it avoids configuring/maintaining max-length constraints and never needs to be widened later if requirements change. **Never store numbers as a character type unless they're codes (ZIP codes, etc.) rather than actual quantities** — character-stored numbers can't be used in math and sort lexically (as text), not numerically.

## Numbers

**Integers**: `smallint` (2 bytes, ±32,767), `integer` (4 bytes, ±2.1 billion), `bigint` (8 bytes, ±9.2 quintillion). Default to `bigint` unless you're certain values stay within `integer`'s range and storage at scale (millions of rows) matters — inserting a number outside a column's range throws an `out of range` error rather than silently truncating.

**Auto-incrementing IDs**: two mechanisms exist. The PostgreSQL-specific `serial`/`bigserial`/`smallserial` types (used in [[sql-creating-databases-and-tables]]'s `teachers.id` column) auto-fill sequential values starting at 1. The ANSI-standard `GENERATED ALWAYS AS IDENTITY` syntax does the same thing in a cross-database-portable way, and additionally **blocks a user from accidentally inserting their own value into the ID column** (the alternative `GENERATED BY DEFAULT AS IDENTITY` allows overriding, which risks duplicate IDs). The book uses `IDENTITY` going forward for portability. Gaps can appear in either scheme's sequence (deleted rows, aborted inserts) — this is normal and not a bug.

**Decimals — fixed-point vs. floating-point**: `numeric(precision, scale)` (equivalently `decimal`) stores an exact value to a specified number of total digits (`precision`) and digits after the decimal (`scale`) — it pads or rounds to match the declared scale exactly. `real` (6-digit precision) and `double precision` (15-digit precision) are floating-point types that store a number as digits-plus-exponent, letting the decimal point "float" — **this representation is provably inexact**: multiplying a `real`-stored 0.7 by 10 million returned 6999999.88079071 instead of 7000000, while the equivalent `numeric` calculation returned the exact value. **Use `numeric`/`decimal` whenever exactness matters (money, anything audited), and floating-point only when storage savings matter more than precision** (e.g., scientific measurements at scale). Default guidance: prefer integers when no fraction is needed; size number columns generously (bigint, ample numeric precision) rather than risk an out-of-range error later.

## Dates and Times

| Type | Storage | Description | Range |
|---|---|---|---|
| `timestamp` | 8 bytes | date + time | 4713 BC–294276 AD |
| `date` | 4 bytes | date only | 4713 BC–5874897 AD |
| `time` | 8 bytes | time only | 00:00:00–24:00:00 |
| `interval` | 16 bytes | a duration (`quantity unit`, e.g. `12 days`) | ±178,000,000 years |

**Always use `timestamp with time zone` (`timestamptz`), not bare `timestamp`, for any event that could be compared across locations** — without a stored time zone, times recorded in different places become impossible to compare meaningfully. Time zones can be specified as an abbreviation (`EST`), a UTC offset (`-8`), or an IANA area/location name (`Australia/Melbourne`) — pgAdmin always displays results normalized to the *querying machine's* time zone, regardless of how the value was entered. `interval` values support direct arithmetic against timestamps (`timestamp_column - interval_column AS new_date`) — useful for calculations like "90 days after the contract date."

## JSON and JSONB

JSON (JavaScript Object Notation) stores structured key/value data, including nested objects, as text. PostgreSQL offers two types: `json` (stores an exact copy of the JSON text) and `jsonb` (stores a binary representation that **supports indexing for faster processing**). JSON entered the SQL standard in 2016; PostgreSQL supported it since version 9.2, with its own additional functions beyond the standard (out of scope for this ingest — see Chapter 16 in the full book if revisited).

## Miscellaneous Types (Noted, Not Covered in Depth)

Boolean (`true`/`false`), geometric types (points, lines, circles — used by PostGIS), text-search types, network address types (IP/MAC), UUID (often used as a key value), range types, binary types, and XML — each exists for a specific specialized use case beyond the core three categories.

## CAST() — Converting Between Types

`CAST(value AS target_type)` converts a value's type — e.g., casting a `timestamp` to `varchar(10)` truncates to the first 10 characters (the date portion, dropping time), or casting a `numeric` to `integer` rounds to a whole number. **CAST only succeeds if the target type can actually represent the value** — casting `text` containing letters to `integer` throws `invalid input syntax for type integer`. PostgreSQL's shortcut double-colon notation (`column::type`) is equivalent but PostgreSQL-specific and won't port to other database systems — the explicit `CAST()` form is the portable choice.

## Key Takeaways

- Default to `text` for character columns and `bigint` for integer columns unless there's a specific reason to constrain size — oversizing costs little; running out of range causes a hard failure.
- Floating-point types (`real`, `double precision`) are mathematically inexact by design — never use them for money or any value requiring exact arithmetic; use `numeric`/`decimal` instead.
- Always store timestamps with time zone information attached (`timestamptz`) for any event that might need cross-location comparison.
- CAST() only succeeds when the target type can represent the source value — it's a good way to deliberately surface malformed data (e.g., text dates that don't actually parse as dates).

# Practical SQL: Table Design that Works for You

**Summary**: Naming conventions for SQL identifiers, the constraint types that enforce data integrity (primary keys — natural vs. surrogate, foreign keys, CASCADE deletes, CHECK, UNIQUE, NOT NULL), how to add or remove constraints on an existing table, and how B-tree indexes speed up queries (with a benchmarked before/after example).

**Sources**: PracticalSQL.pdf (Anthony DeBarros, 2nd ed., 2022), Chapter 8 ("Table Design that Works for You")

**Last updated**: 2026-06-20

## Naming Conventions

PostgreSQL treats unquoted identifiers as lowercase regardless of how they're typed — `customers` and `Customers` collide unless the second is wrapped in double quotes to preserve case. **Quoting also enables spaces and reserved keywords as identifiers, but this is a trap**: every later reference to that identifier must also be quoted, or the database throws an error (worse, it may misparse an unquoted multi-word name as two separate identifiers). The author's recommended defaults: **use snake_case** (readable, matches PostgreSQL's own documentation, avoids the quoting problem entirely), use full descriptive names over cryptic abbreviations, **pluralize table names** (a table holds many rows of one entity — `teachers`, not `teacher`) except when preserving an imported CSV's original name for a one-off import, keep names reasonably short (PostgreSQL's identifier limit is 63 characters; older Oracle systems cap at 30 — lean short if code might be ported), and append a `_YYYY_MM_DD` suffix to table copies so they both stay distinguishable and sort in date order.

## Constraint Types

Constraints supplement a column's data type with rules and logical tests, defending against "garbage in, garbage out." Beyond primary/foreign keys (introduced in [[sql-joining-tables-and-relationships]]), three more constraint types exist: **CHECK** (only allows rows where a supplied Boolean expression evaluates true), **UNIQUE** (values in a column or column group must be unique per row, but unlike a primary key, multiple `NULL`s are allowed), and **NOT NULL** (disallows empty values in a column). Constraints can be declared as a **column constraint** (inline with the column's type, applies to just that column) or a **table constraint** (declared after all columns, can span multiple columns — required for any composite/multi-column constraint).

## Primary Keys: Natural vs. Surrogate

A **natural key** uses an existing column (or columns) that's already unique and never empty — a product code, ISBN, or serial number. Advantages: no extra column needed, and the key's inherent meaning can reduce the need for joins. Risk: if the data later violates the key's uniqueness assumption, the table structure has to change. A **composite primary key** combines multiple columns when no single column is unique enough alone (e.g., a driver's license ID is only unique *within* a state, so `(license_id, state)` together form the natural key) — declared only via the table-constraint syntax, columns listed comma-separated in parentheses.

A **surrogate key** is an artificial, autogenerated column (typically `bigint GENERATED ALWAYS AS IDENTITY`) used when no natural key exists. Advantages: guaranteed uniqueness, and the table's structure is decoupled from the data, so it isn't disrupted if the data changes. Cost: an extra column and the storage it requires. **UUIDs** (32-hexadecimal-digit identifiers, often used for hardware/software IDs) are an alternative surrogate format, but the author explicitly warns they're inefficient compared to `bigint` for a typical primary key.

`GENERATED ALWAYS AS IDENTITY` blocks manual inserts into the auto-incrementing column by default; manually inserting a specific value requires the `OVERRIDING SYSTEM VALUE` keywords in the `INSERT`, followed by `ALTER TABLE ... ALTER COLUMN ... RESTART WITH n` to re-sync the sequence so the next auto-generated value doesn't collide. **Deleting a row never backfills the gap in the sequence** — gaps in ID sequences are normal, not a bug.

## Foreign Keys and CASCADE

A foreign key column's values must already exist in the referenced table's primary key (or other unique) column — this enforces **referential integrity**, preventing orphaned rows. Practical consequences: **rows must be inserted into the referenced table before the referencing table** (you can't register a vehicle to a license that doesn't exist yet), and conversely, **a referenced row can't be deleted while related rows still exist** unless `ON DELETE CASCADE` is added to the foreign key definition — which tells PostgreSQL to automatically delete dependent rows when their referenced row is deleted, avoiding having to manually clean up related tables first.

## CHECK, UNIQUE, and NOT NULL in Practice

`CHECK (column IN ('Admin', 'Staff'))` and `CHECK (salary >= 0)` are typical column-level checks; a table-level `CHECK` can combine multiple conditions with `AND`/`OR` or compare two columns directly (e.g., `CHECK (sale_price < retail_price)`). `UNIQUE` is the right choice over a primary key whenever a column should be unique-when-present but may legitimately be empty for some rows (e.g., an optional but de-duplicated email column). `NOT NULL` is the simplest constraint — it just requires a value, useful for columns like first/last name that should never be blank.

**Constraints can be added to or removed from an existing table** with `ALTER TABLE table_name DROP CONSTRAINT constraint_name` / `ADD CONSTRAINT ...`, or for `NOT NULL` specifically, `ALTER TABLE table_name ALTER COLUMN column_name DROP NOT NULL` / `SET NOT NULL`. **Adding a constraint to an existing table only succeeds if the table's current data already satisfies it** — e.g., you can't retroactively add a primary key to a column that already contains duplicates.

## Speeding Up Queries with Indexes

An index is a separate data structure the database maintains alongside a table, letting a query find matching rows without scanning every row (a *sequential scan*). PostgreSQL's default index type is the **B-tree** (balanced tree) — automatically created for every primary key and `UNIQUE` constraint, and also the default type for an explicit `CREATE INDEX` statement. B-tree indexes work well with equality/range operators (`= < <= >= > BETWEEN`) and with `LIKE` patterns that don't start with a wildcard. PostgreSQL also offers other index types (GIN, GiST) suited to full-text search and geometric data — out of scope for this ingest.

`EXPLAIN ANALYZE` in front of any query shows its **query plan** plus actual measured execution time — the tool for benchmarking whether an index is actually helping. A real measured example on a 940,374-row NYC address table: searching `WHERE street = 'BROADWAY'` took ~92ms via a sequential scan; after `CREATE INDEX street_idx ON new_york_addresses (street);`, the same query dropped to ~5ms using an index scan — roughly an 18x speedup. `DROP INDEX index_name` removes an index that turns out not to be used or needed.

**Indexes aren't free** — they enlarge the database and add overhead to every insert/update/delete (the index must be kept current). Guidance for when to add one: index columns that get joined on (primary keys are auto-indexed, but **foreign key columns in the referencing table are not** and are worth indexing manually, especially to avoid a slow sequential scan during a cascading delete), index columns that frequently appear in a `WHERE` clause, and use `EXPLAIN ANALYZE` to verify the index is actually being used before keeping it.

## Key Takeaways

- Default to snake_case, plural table names, and short descriptive identifiers to avoid the entire quoting/case-sensitivity problem class.
- Prefer a natural key when the data genuinely supports one (less storage, fewer joins); fall back to a surrogate (`bigint GENERATED ALWAYS AS IDENTITY`) when no column or column combination is reliably unique and non-empty.
- `ON DELETE CASCADE` on a foreign key is the standard way to let a parent-row deletion automatically clean up dependent child rows, instead of manually deleting them in dependency order.
- Index columns used in joins (especially foreign keys, which aren't auto-indexed) and columns frequently filtered in `WHERE` clauses — but verify the benefit with `EXPLAIN ANALYZE` rather than indexing everything by default.

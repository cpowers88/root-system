## 1. Executive Verdict

Keep the existing System Loop, Return Packet, eight information states, domain ownership, and ten functional roles. They already form a coherent architecture for moving evidence into knowledge, capability, action, measured value, and system learning.

Modify the skeleton proposal in four bounded ways before any migration:

1. Treat CASTLE elevation as a hypothesis to validate with an impact report and a no-write dry run, not as an architectural requirement already proved.
2. Keep Watchtower separate from CASTLE. Watchtower senses external change; CASTLE decides internal sequence. Their handoff should be tested, not their ownership merged.
3. Replace the single broad `path_reference_audit.py` concept with a shared scanning library and four explicit checks: path moves, resolvable references/anchors, canonical-copy violations, and declared instruction-register conformance.
4. Add a migration control section covering dependency discovery, performance budget, failure recovery, rollback trigger, fresh-session acceptance, and a post-change `check_at`.

Do not add another lifecycle, metadata plane, state machine, or research layer. Do not ingest all eight new books merely to complete this report. Four were only sampled in the governing proposal; the other four remain unactivated because their full ingestion would exceed the named architecture questions and violate the smallest-evidence rule.

**Decision:** the design is directionally correct but not yet implementation-ready. The next gate is a deterministic, read-only CASTLE-move impact report.

## 2. What the Current Skeleton Gets Right

- **One lifecycle and one return packet.** `ROOT_CAPABILITY_CONTRACT.md` already connects SENSE through EVOLVE and requires outcome, evidence, status movement, reusable-asset candidacy, and system-learning candidacy.
- **One information-state translation.** `ROOT_INFORMATION_FLOW_CONTRACT.md` maps Intent through Learn onto the System Loop, five-move task protocol, knowledge-to-value pipeline, and review cadence without defining a competing cycle.
- **Owner truth stays with the domain.** The wiki contracts and CASTLE operating rules consistently separate research/learner truth from sequencing and proof status.
- **Functional roles describe purposes rather than folder names.** The ten-role taxonomy survives renames and exposes the real distinction between governance, direction, decision, sensing, knowledge, projects, reusable business assets, intake, privacy, and history.
- **Root entry surfaces remain interfaces.** Keeping `NOW.md`, `START_HERE.md`, brief files, and AI pointers at root avoids inventing an eleventh content realm.
- **Raw evidence remains immutable.** This is reinforced in the universal wiki layer and the hub contracts.
- **Human approval remains attached to consequential change.** Generated reports and proposals are not treated as implementation, mastery, demand, or profit.
- **The design begins from three real stale-reference failures.** The proposed validator responds to demonstrated defects rather than abstract elegance.
- **Instruction-register work begins from an existing successful distinction.** `AGENT.md` and `CHRIS_CORE.md` already show that executable rules and human context can differ without separate directory trees.
- **The design rejects duplicate machine-readable doctrine and unnecessary CASTLE state labels.** That protects one source of truth and avoids new stale state.

## 3. Material Weaknesses or Missing Mechanisms

### 3.1 CASTLE elevation is not yet causally proved

The proposal establishes that CASTLE has a distinct function. It does not establish that nesting under `00-BRAIN` currently causes enough navigation, loading, ownership, or maintenance failure to justify a high-reference path move. A role distinction does not automatically require a top-level directory.

### 3.2 The validator spec combines different failure classes

Literal path replacement, dead references, duplicate canonical files, missing headings, and prose-shape regressions share a scanning substrate but require different truth models:

- path-move audit knows an explicit old/new pair;
- link/anchor audit resolves current targets;
- canonical-copy audit needs a declared canonical home or content hash;
- register lint evaluates declared document structure.

One monolithic command would make failure meaning, baselines, and ownership unclear.

### 3.3 Migration controls are incomplete

The proposal needs:

- an authoritative live-reference classification;
- a dependency inventory before moving;
- a runtime/performance ceiling for vault-wide checks;
- explicit abort and rollback triggers;
- verification that historical references remain historical;
- a fresh-session boot test from each active AI surface;
- a named observation date after normal use.

### 3.4 Source-accounting maturity is uneven

AI_AUTOMATION_SYSTEMS, SYSTEMS, and TECHNOLOGY have explicit source-disposition ledgers. BUSINESS, EDUCATION, PHYSICS, PYTHON, and REVENUE_LAB do not have equivalent all-source ledgers; their logs and, where present, source maps are substitutes. This is a discoverability gap, not evidence that five new ledgers should be created immediately.

### 3.5 The register proposal needs a validator before broad rollout

Adding `register:` without a query, validator, or adoption boundary creates metadata debt. Pilot it only on governance/instruction files, define minimum conformance rules for each value, and test whether it catches flag #83-class regressions without forcing unnecessary companion files.

### 3.6 Knowledge-to-value visibility is contractual but not yet tested in routing

The Capability and Information Flow contracts distinguish capability, use, value, willingness to pay, revenue, and reusable assets. The skeleton should point to those contracts rather than restate them. A routing scenario set should prove fresh sessions can follow the path without premature monetization.

## 5. Eight-Lens Findings

### Lens 1 — Acquisition and provenance

**Finding:** keep immutable raw, source-tiering, recency markers, contradiction classification, and owner-specific evidence homes. Modify intake language so `77-INBOX` is the universal external arrival door while hub `raw\` remains an evidence boundary after owner identification, not an alternative intake door.

**Test:** route ten mixed arrivals; each has one temporary intake location, one eventual owner, and no raw write before ownership is known.

### Lens 2 — Parsing, classification, synthesis, and retrieval

**Finding:** the raw→wiki→index/log pattern is validated, but compilation can lose information and cost more than targeted retrieval. Keep selective activation, chunk boundaries, negative findings, and explicit source disposition. Do not turn “fully accounted” into “fully compiled.”

**Test:** answer a fixed probe set from one compiled hub and trace each answer to source coverage; record misses before considering new retrieval tooling.

### Lens 3 — Education and capability

**Finding:** the skeleton should not claim that stored knowledge becomes capability. Capability requires independent retrieval, explain-back, construction, debugging, application, or transfer, returned to the learning owner.

**Test:** a fresh session can distinguish “page exists,” “Chris practiced,” “Chris performed independently,” and “used successfully” for one Python and one Physics example.

### Lens 4 — Workflow and systems analysis

**Finding:** roles are distinguishable when defined by transformation and authority, not content topic. CASTLE can oversee cross-wiki investigations if it stores question, owner, proof, gate, and return path only.

**Test:** a cross-wiki architecture investigation leaves primary findings in owners and only the integrated verdict/status in CASTLE.

### Lens 5 — Technical architecture and lifecycle

**Finding:** use one scanning library with separate validators. Add normalized path handling, Markdown link/anchor parsing, canonical declarations/hashes where needed, exclusions, JSON output, baselines limited to historical narrative, and performance telemetry.

**Test:** fixtures reproduce the three stale-path incidents, flag #83, one legitimate historical mention, one duplicate filename with different content, and one byte-identical duplicate.

### Lens 6 — Implementation and migration

**Finding:** migration must be staged: inventory → dry run → approval → preserved snapshot/archive → move → reference updates → validators → fresh-session tests → observation period. The move is reversible until normal work creates new post-move state.

**Test:** zero unresolved active references, no duplicate authority, boot and local contracts resolve, health adds zero new debt, and a rollback rehearsal identifies every step.

### Lens 7 — Business and value

**Finding:** the architecture adds economic value only when it reduces search/rework, improves dependable delivery, protects trust, or creates reusable sanitized assets. Folder elegance is not value. Capability, use, willingness to pay, revenue, and repeatability must remain separate states.

**Test:** one real workflow records time-to-find, defect/rework count, delivery result, user/client response, money received if any, and reusable-asset decision.

### Lens 8 — Human-governed evolution

**Finding:** keep research→proposal→approval→implementation→validation→`check_at` outcome. Add observability for validator runtime, false positives, misses, and operator burden. No unattended self-rewrite.

**Test:** a fresh session discovers the proposal, authority, checks, observed outcome, and keep/modify/revert verdict without oral history.

## 6. Contradictions and Uncertainty

- **CASTLE role versus location:** evidence strongly proves CASTLE is a distinct function; it only weakly proves top-level relocation is necessary.
- **One universal intake door:** `77-INBOX` works for external arrivals, but hub raw boundaries and CASTLE’s current triage staging can appear as competing doors. The distinction must be stated as arrival versus owned evidence/decision staging.
- **One validator versus several:** a unified command is convenient, but failure semantics differ. Shared engine plus separate checks resolves the tension.
- **Instruction register:** source evidence supports audience- and model-aware instruction design, but the proposed two-value metadata field may oversimplify mixed interfaces. Pilot evidence is missing.
- **Ten roles:** no mandatory eleventh role emerged. “Deployment/integration” is a System Loop stage performed in projects/client work, not a separate storage realm. However, real routing cases could expose overlap between reference/project deliverables and staged research.
- **Watchtower separation:** three internal analyses converge on separate ownership, but no observed operational comparison exists. Confidence is high on separation of concerns, moderate on the final folder name/location.
- **Book batch:** the four newly sampled sources cannot support broad architecture conclusions beyond the exact extracts already recorded. Four books were not examined for this report.

## 7. Recommended Final Architecture

Use the current physical tree until the migration gate passes. Adopt this logical architecture now as the review model:

1. `00-BRAIN` — AI governance and coordination.
2. `01-NORTH_STAR` — durable direction and system contracts.
3. CASTLE — decision, sequencing, proof status, and integration pointers.
4. Watchtower — external sensing and materiality-qualified signals; separate from CASTLE.
5. `03-WIKIS` — bounded research and learner truth.
6. `02-LIBRARY` — reference, course files, and deliverable-bearing projects.
7. `05-BUSINESS` — sanitized reusable business assets.
8. `77-INBOX` — sole external arrival door.
9. `88-JOURNAL` — private, never accessed by AI.
10. `99-ARCHIVE` — preserved inactive history.

Keep root entry surfaces outside the role tree. Keep the System Loop and eight-state information contract as the only lifecycle and translation system.

For integrity tooling:

```text
shared scanner/parsers
├─ move audit: explicit old/new path pairs
├─ reference audit: current file, wikilink, Markdown link, and heading anchors
├─ canonical-copy audit: designated owner, hashes, duplicate/collision cases
└─ register lint: schema and structure for declared instruction files
```

Each check gets its own exit code category and baseline. A wrapper may run all checks, but it must not erase which invariant failed.

# Review 02 — Lyz's Blue Book

## Source

- Repository: [lyz-code/blue-book](https://github.com/lyz-code/blue-book)
- Project lifecycle page: [docs/projects.md](https://github.com/lyz-code/blue-book/blob/master/docs/projects.md)
- Navigation configuration: [mkdocs.yml](https://github.com/lyz-code/blue-book/blob/master/mkdocs.yml)
- Accessed: 2026-08-07

## Why it was selected

The Blue Book is a mature, broad personal wiki with projects, technical
knowledge, life systems, and a published web interface. Its scale makes it both
a useful analogue and a warning.

## What the system does well

- Uses a memorable project lifecycle—seed, blooming, and dying plant—to make
  maturity visible.
- Records operational attributes such as priority, last update, expected end,
  recurrence, and whether an item still bothers the owner.
- Distinguishes sources and gives attention to source quality.
- Treats publishing/search as an interface over the underlying knowledge.

## What `.ROOT V2` should take

1. Use a small, universal lifecycle for knowledge and opportunities. Proposed
   terms for `.ROOT`: `captured -> understood -> tested -> proven -> packaged`.
2. Add aging and next-decision dates to active initiatives so old plans become
   visible instead of silently remaining current.
3. Rank sources by authority and directness before AI synthesis.

## What not to copy

- A very large hand-maintained navigation tree becomes a second knowledge base
  that must stay synchronized with the first.
- A long list of possible tools and projects can look like capability while
  remaining unbuilt and unvalidated.
- Repository scale and publishing breadth do not demonstrate economic outcomes.

## Root-specific inference

The Blue Book resembles `.ROOT`'s present risk: useful breadth can accumulate
faster than proof. V2 should generate navigation from metadata and links, and
it should prevent “idea” from being confused with “active,” “tested,” or
“revenue-capable.”

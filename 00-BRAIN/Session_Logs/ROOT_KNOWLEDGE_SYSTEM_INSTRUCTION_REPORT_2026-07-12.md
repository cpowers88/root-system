# .ROOT Knowledge-System Instruction Report

## Executive Verdict

`.ROOT` already has the right top-level architecture. Do **not** merge the seven `03-WIKIS` hubs, CASTLE, or the Capability Library, and do not add another wiki.

The strongest operating flow is:

```text
source evidence -> domain wiki -> CASTLE commitment -> work/proof
                -> reusable capability asset -> client use
                -> field evidence back into the relevant wiki
```

The three systems have different jobs:

1. **Wikis refine and retrieve knowledge.**
2. **CASTLE sequences commitments and proof.**
3. **The Capability Library packages proven methods for reuse.**

The next improvement is not structural expansion. It is a clearer operating contract and repair of human-interface drift: several guides and current-position statements no longer match the live tree.

## 1. Canonical Mental Model

Use `.ROOT` as four stacked layers:

```text
COMMAND     00-BRAIN + 01-NORTH_STAR
            Governs, prioritizes, approves, and sequences

KNOWLEDGE   03-WIKIS
            Refines sources into domain knowledge and learning paths

PROOF       02-LIBRARY projects / school work / field observations
            Demonstrates that knowledge can be used

VALUE       05-BUSINESS, especially 06-Capability Library
            Packages proven methods into reusable client value
```

Authority flows downward: North Star -> governance -> CASTLE -> active realm. Evidence flows upward: work -> proof -> wiki update -> CASTLE status -> reviews. No lower layer silently rewrites a higher layer.

## 2. The Three Knowledge-System Classes

| Class | Systems | Primary question | Must not become |
|---|---|---|---|
| Domain refinery | Seven `03-WIKIS` hubs | What is useful in this domain, and what should be learned or applied next? | Command center, client-file store, general dump |
| Direction system | `00-BRAIN\CASTLE` | What comes next, why, and what proof closes it? | Deep refinery, course wiki, business wiki, daily task manager |
| Capability packaging | `05-BUSINESS\06-Capability Library` | What proven method can be reused in paid work? | Wiki, source-note folder, one-client folder, idea backlog |

This distinction should anchor two future instruction sets: a concise human guide for Chris and a precise AI operating contract.

## 3. Shared Operating Contract for All Seven Wikis

The universal rules correctly live once in `00-BRAIN\AGENT.md`; do not copy them back into every hub.

### Start

1. Open `wiki/index.md`.
2. Read the last three `wiki/log.md` entries.
3. Read `current-position.md` and the domain path/map when the hub has an active frontier.
4. State one session objective and expected output.

### Work

1. Search before creating; prefer updating.
2. Treat every `raw\` folder as immutable evidence.
3. Extract only what serves the hub's controlling question.
4. Preserve provenance and date volatile claims.
5. Separate generated content from demonstrated learning or field proof.
6. Route cross-domain conclusions by link or targeted update; never duplicate permanent doctrine.

### Close

1. Append `wiki/log.md`.
2. Update `wiki/index.md` only when navigation changed.
3. Update `current-position.md` only when the real frontier moved.
4. State the next exact action.
5. Let weekly CASTLE sweeps detect light drift; use monthly lint for links, indexes, contradictions, stale claims, and orphans.

## 4. Best Use of Each `03-WIKIS` Hub

### SYSTEMS — diagnostic and ISYE method library

Use it to retrieve system dynamics, factory physics, queuing, inventory, process mining, APQC, BPMN, VSM, and operations-research concepts that improve coursework or an operational diagnosis. Translate each concept into a diagnostic question, measurable relationship, or client observation.

SYSTEMS explains operational mechanics. BUSINESS turns them into an offer. CASTLE decides when the skill matters. The Capability Library packages a proven diagnostic.

**Drift:** `HOW_TO_USE.md` says 41 pages while the index says 74 and the live inventory contains roughly 78 wiki files.

### PYTHON — sequential programming education engine

Work the current stage through concept -> drill -> mini-project -> proof. The live frontier is Stage 1; generated Stages 2–10 are inventory, not mastery. Use `current-position.md` -> `learning-path.md` -> one stage packet.

The wiki teaches and records learning. Real codebases live locally and on GitHub. Reusable client patterns graduate to the Capability Library only after testing.

**Drift:** `wiki/index.md` is titled “Education Wiki Index,” a high-salience identity error.

### EDUCATION — general KSU coordination and study support

Use it for TCOM, ECON, ENGR, and subjects that do not justify their own hub. Actual course files remain in `02-LIBRARY\00-SCHOOL`. Activate course-specific structures only when D2L and real coursework create demand.

**Drift:** `HOW_TO_USE.md` calls the hub empty, but it now contains course briefs, an AI-programs reference, and an active pre-semester current-position page.

### PHYSICS — staged situation-to-model learning engine

Use `current-position.md` -> stage page -> concept/equation/problem type -> worked example -> drill -> common error -> mastery check. Generated packets remain unmastered until Chris demonstrates them. The live frontier is Stage 3, Vectors.

**Conflict:** CASTLE's `current-position.md` says Physics is stale at Stage 1, while the Physics source of truth says Stage 3. The downstream summary must reconcile to the domain owner.

### BUSINESS — strategy and blank-master layer

Use it to turn SYSTEMS, TECHNOLOGY, and AI research into offers, audit methods, pricing, sales, fulfillment, and human-agent operating models. Work the current phase edge, not the whole long-range page set. When a master is used for a prospect or client, the filled artifact moves to `05-BUSINESS`; reusable lessons return to the wiki.

**Interface need:** name one canonical phase-status page in the human guide so strategy browsing does not replace action.

### TECHNOLOGY — landscape radar plus applied technical reference

Explicitly choose one of two session modes: `landscape decision` (“should this be learned or recommended now?”) or `applied retrieval` (“how does this work?”). The inherited applied pages are reference inventory, not a curriculum queue.

New AI/agent research goes to AI_AUTOMATION_SYSTEMS. Applied Python learning goes to PYTHON. Profit ideas go through the CASTLE gate.

### AI_AUTOMATION_SYSTEMS — research and self-evolution proposal lab

Use it for evidence on AI tools, agents, MCP, automation patterns, safety, and `.ROOT` friction. The promotion loop is research -> evidence page -> bounded proposal -> Chris/review cadence -> approved governance change. The wiki never governs unilaterally.

**Drift:** `HOW_TO_USE.md` still calls this an empty scaffold although the index records a mature research set and two completed proposal-to-promotion loops.

## 5. Best Use of CASTLE

CASTLE is the integration layer, not an eighth domain wiki. Keep it small, decisive, and pointer-heavy.

Use it for the roadmap, current position, phase gates, skills tied to services and proof, opportunity gates, source summaries that change sequencing, weekly cross-wiki movement, monthly drift review, and ownership of `.ROOT\NOW.md`.

Do not use it to teach a subject, store business doctrine, duplicate wiki pages, or track every daily task. A CASTLE entry should answer **why now**, **what proof**, and **what next**.

**Live drift:** CASTLE's README uses “top .01% output,” while the canonical North Star and profile use “top 1%.” Replace copied mission language with a pointer. CASTLE's Physics status also trails the domain source of truth.

## 6. Best Use of the Capability Library

The Capability Library is a productization boundary. An item enters only after this gate:

```text
repeated method + multi-client reuse + owner-understandable use case
+ APQC/process mapping + named validation test + next packaging action
```

Use the maturity ladder: `idea -> draft -> tested internally -> client-ready -> deployed`.

Promotion loop:

1. Source insight stays in its wiki or audit template.
2. A proof project or field observation tests it.
3. A generic version is instantiated from `APQC_ASSET_TEMPLATE.md`.
4. The index records maturity, source, use case, and next action that day.
5. Client-specific copies live in the engagement area.
6. Field results update the asset and originating wiki claim when needed.

The structure is ready, but the index contains only the template. The proposed first asset—an APQC workflow observation map—is the correct next candidate after approval.

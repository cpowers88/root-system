# Weekly System Improvement Recommendations — August 2, 2026

## Recommendation

Run one seven-day operating pilot aimed at a **10–20% improvement in proof-to-control efficiency**. Do not redesign `.ROOT`, add a dashboard, or open another architecture program. The target is fewer control-plane touches per completed learner or value proof.

## Why this wins now

The vault can already orient, teach, gate, log, validate, and preserve evidence. This week it completed about 41% of its planned weekday school blocks while producing extensive system work. The bottleneck is conversion, not missing capability.

The recurring failure chain was:

```text
owner proof changes
    -> dashboard/plan does not fully update
    -> next session reloads and reconciles
    -> another report or repair is produced
    -> planned proof loses time
```

## Seven-Day Pilot

### 1. First-proof lock

Begin each active day with one named learner or real-workflow artifact. Optional system work waits until it closes. Only a HIGH blocker or Chris's direct redirect interrupts it.

### 2. One-load / one-close rule

Use one full governed load at the first session of the day. Later sessions read only `NOW.md`, the active owner page, and its newest log entry unless they conflict. At close, update owner truth first, then append one concise DAILY packet, then refresh the cockpit once if the next action changed.

### 3. Frontier propagation as an acceptance check

When a stage or gate closes, the same close is incomplete until:

- the owner current-position states the new frontier;
- `NOW.md` or `MORNING_BRIEF.md` exposes that frontier;
- the prior next action is no longer presented as live.

This is the recommended resolution pattern for flag #91. It should be implemented as a small interface rule after Chris approves the exact wording, not as a new dashboard.

### 4. Evidence-sized weekly plan

Commit only the core blocks supported by the prior week's demonstrated throughput; label additional blocks as stretch. The prior plan's 32 blocks measured theoretical capacity, not sustainable throughput. A smaller honest commitment will generate better planning evidence than another inflated target.

### 5. Maintenance quarantine

During Monday–Saturday, only HIGH health/integrity failures interrupt proof. MEDIUM and LOW flags, source intake, architecture review, and tool exploration wait for Sunday. When a HIGH issue appears, repair the smallest boundary and return to the proof lane.

## Measurements

Use existing DAILY and weekly-plan files; create no tracker.

- completed core proof blocks;
- control-plane touches: full load, dashboard refresh, reconciliation, audit/report, handoff, or repair;
- proof blocks displaced by system work;
- stale or false `closed`, `fixed`, `committed`, `pushed`, or `verified` claims;
- frontier changes that reached the cockpit in the same close.

## Acceptance on August 9

Keep the pilot if all are true:

- at least 85% of committed **core** proof blocks close;
- control-plane touches per proof fall 10–20% from this week's reconstructed baseline;
- zero optional system work displaces the day's first proof;
- zero unsupported completion claims survive the same session;
- every stage/frontier change reaches the cockpit at close;
- one bounded workflow result is usable by another person or explicitly fails with classified evidence.

Modify or reject the pilot if it adds recording burden without reducing reconciliation or displacement.
